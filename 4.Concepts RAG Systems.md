## Pretraining vs Fine-tuning vs Instruction FT vs RAG

> (ONE GOAL, FOUR LEVERS)

---

### Overview & Core Concepts

- **Pretraining**
  - Train a model from scratch on massive unlabeled text via next-token prediction.
- **Fine-tuning**
  - Continue training a base model on smaller domain or task-specific data.
- **Instruction FT**
  - Fine-tune on (instruction $\rightarrow$ response) pairs so the model follows directions; often + RLHF.
- **RAG (Retrieval-Augmented Generation)**
  - Retrieve relevant text at query time and inject it into the prompt — no training at all.

---

### Comparison Matrix

| Approach           | Weights         | Data                      | Cost                | Output             |
| :----------------- | :-------------- | :------------------------ | :------------------ | :----------------- |
| **Pretraining**    | Built from zero | Trillions of tokens       | $$$ — weeks of GPUs | A base model       |
| **Fine-tuning**    | Updated         | $10^3$–$10^6$ labeled ex. | $$ — hours to days  | Specialized model  |
| **Instruction FT** | Updated         | Curated instructions      | $$ + alignment      | Chat / assistant   |
| **RAG**            | Unchanged       | Your live KB              | $ — infra only      | Grounded + sources |

---

> 💡 **Rule of thumb:** Change the weights when you need new behaviour or skills; reach for RAG when you need fresh, private, or citable knowledge.

## RAG AS AN APPROACH

Augmenting the model at query time instead of retraining it. The facts come from an external knowledge base.

---

### Overview

- **WHAT**

  - Retrieve relevant external documents at query time and add them to the prompt. The model weights stay unchanged.

- **PROS**

  - Always-fresh knowledge, source citations, no retraining, and fewer hallucinations.

- **CONS**

  - Depends on retrieval quality; adds latency; bounded by the context window.

- **WHEN**
  - Knowledge changes often, you need traceability, or you have large proprietary corpora.

---

### Components of RAG

| Component             | Function                                                                 |
| :-------------------- | :----------------------------------------------------------------------- |
| **Retriever**         | Finds and pulls the most relevant information from trusted data sources. |
| **Generator**         | Uses LLMs to turn retrieved data into clear, natural language responses. |
| **Knowledge Base**    | A storage space that holds all reference data for RAG models to use.     |
| **Integration Layer** | Connects all components to ensure smooth and efficient operation.        |

3# VECTOR DATABASES
Specialized stores that index and search high-dimensional embeddings by meaning. The engine behind RAG retrieval.

---

### Core Concepts

- **WHAT**

  - A database purpose-built to store and search high-dimensional embedding vectors and not rows, keys, or text.

- **WHY**

  - Keyword & SQL search can't match by meaning. Vector DBs enable fast semantic search across millions–billions of vectors.

- **HOW IT WORKS**

  - Embed data $\rightarrow$ store vectors + metadata $\rightarrow$ build an ANN index $\rightarrow$ query by nearest neighbors (cosine / L2).

- **KEY FEATURES**
  - ANN indexing, metadata filtering, CRUD & upserts, horizontal scaling, and hybrid (keyword + vector) search.

---

### Data Pipeline & Architecture

#### 1. Raw Data

> Docs, images, audio, code

↓

#### 2. Embedding Model

> Convert to dense vectors

↓

#### 3. Vector DB

> Index (HNSW / IVF) + metadata

↓

#### 4. ANN Query $\rightarrow$ Top-k

> Nearest-neighbor matches

---

> 💡 **Powers:** RAG · semantic search · recommendations · dedup

## Types of Vector Databases

Three families that range from purpose-built engines to plugins on databases you already run, to lightweight in-process libraries.

| :----------------------- | :---------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------- |

## Chunking

**Why Chunking Matters?**

In Retrieval-Augmented Generation (RAG), chunking is the process of breaking large documents into smaller, manageable text segments. Chunking is the single biggest quality lever in your RAG pipeline. It determines the granularity of retrieval and the context quality provided to the LLM.

## Chunking Strategies

_How you split documents before embedding — the single biggest lever on retrieval quality._

### 1. Fixed-Size

Split every N tokens / characters. Simple and fast, but may cut mid-idea — add 10-20% overlap.

### 2. Recursive Character

Split on a hierarchy: paragraphs → sentences → words. Preserves structure (LangChain default).

### 3. Sentence / Paragraph

Break on natural language boundaries for coherent, self-contained units of meaning.

### 4. Sliding Window

Overlapping chunks that carry context across boundaries and reduce lost information.

### 5. Semantic

Split where meaning shifts using embedding similarity. Best relevance, higher cost.

### 6. Document-Based

Split by structure: Markdown headers, code functions, tables, and sections.

---

**Tip:** match chunk size to your embedding model & query type • balance recall vs. precision • always test retrieval quality

## Strategy 1: Fixed-Size Chunking

## The Logic

Splits text into segments based strictly on a character or token count (e.g., 512 tokens). It is the most deterministic and common baseline method.

## Strategy 2: Semantic Chunking

### Process & Logic

1. **Segment Document:** Divide the document into base units (sentences or paragraphs).
2. **Evaluate Cosine Similarity:** Build the initial chunk and continuously append new segments until cosine similarity drops drastically.
3. **Establish Boundaries:** Lock in the final chunk at the drop point and begin the next chunk with the adjacent segment.

---

### Visual Progression & Breakpoint Analysis

The cosine similarity curve plotted against **Sentence Progression** illustrates context boundaries:

- **Breakpoint (Anomaly):** Indicates an anomalous dip in cosine similarity between consecutive sentences.
- **Topic Shift:** Highlights the exact point where the overarching theme transitions.

#### Text Breakdown Example

- **Chunk 1 (AI Focus):** _"Artificial intelligence is transforming industries by automating processes, enhancing decision-making, and providing insights through data analysis."_
- **Chunk 2 (ML Focus):** _"Machine learning, a subset of AI, enables systems to learn and improve from experience without explicit programming."_
- **Chunk 3 (Deep Learning Focus):** _"Deep learning, a branch of machine learning, uses neural networks with multiple layers to model complex patterns in data."_

---

### Mechanism: The Isolation Forest

Instead of fixed thresholds, **Isolation Forests** can identify anomalous drops in cosine similarity between sentences. These anomalies mark the "outliers" in semantic continuity, pinpointing exact locations where the topic changes.

## Semantic Chunking: Pros and Cons

### 1. The Value

- **Description:** Ensures that every chunk retrieved is a self-contained semantic unit.
- **Best For:** Highly effective for dense, unstructured text like long-form reports.

---

### 2. Isolation Forest

- **Pros:** Unsupervised anomaly detection for split points.
- **Cons:** Requires embedding every sentence first, increasing overhead.

---

### 3. Detailed Example

- **Scenario:** Splitting a medical journal when the text moves from `"Clinical Symptoms"` to `"Statistical Significance"`, even without an explicit header.

## Strategy 3: Recursive Chunking

### The Logic

Uses a hierarchical list of separators to split text. It tries to keep paragraphs together, then sentences, and finally words until the chunk size limit is met.

- **Separators:** `["\n\n", "\n", " ", ""]`

---

### Process Flow

1. **Segment Document:** Break text into initial paragraphs or thematic sections.
2. **Select Segment:** Evaluate chunk against size constraints.
   - **Size > chunk-size limit:** Split further recursively using the next separator down the hierarchy.
   - **Size <= chunk-size limit:** Retain chunk as-is.

---

### Example

In a research paper, it splits at a section break first. If the section is too large, it splits down to the paragraph level.

#### Text Breakdown

- **Paragraph 1:** _"Artificial intelligence is transforming industries by automating processes, enhancing decision-making, and providing insights through data analysis. Machine learning, a subset of AI, enables systems to learn and improve from experience without explicit programming. Deep learning, a branch of machine learning, uses neural networks with multiple layers to model complex patterns in data."_
- **Paragraph 2:** _"AI is also improving natural language processing, enabling applications like chatbots and virtual assistants."_

## Overview

This document summarizes the text chunking and retrieval strategies used in Retrieval-Augmented Generation (RAG) pipelines, comparing their granularity, coherence, cost, and ideal use cases.

## Strategy Comparison Matrix

| Strategy       | Granularity  | Coherence   | Cost       | Primary Use Case          |
| :------------- | :----------- | :---------- | :--------- | :------------------------ |
| **Fixed-Size** | Token Count  | Low         | Very Low   | Baseline / Simple Text    |
| **Recursive**  | Paragraph    | Medium-High | Low        | Standard RAG Docs         |
| **Semantic**   | Topic-based  | High        | Medium     | Research / Long Articles  |
| **Document**   | Header-based | High        | Low-Medium | Manuals / Tech Docs       |
| **LLM/Agent**  | Contextual   | Exceptional | High       | Complex Legal / Financial |

---

## Breakdown of Chunking Strategies

- **Fixed-Size Chunking**

  - **Granularity:** Fixed token or character counts (e.g., 256 or 512 tokens).
  - **Coherence:** Low (can split context or sentences mid-thought).
  - **Cost:** Very Low.
  - **Best For:** Quick benchmarks, simple unformatted text, or low-budget baseline implementations.

- **Recursive Chunking**

  - **Granularity:** Paragraphs, sentences, or natural logical boundaries.
  - **Coherence:** Medium to High (preserves semantic units by attempting hierarchical splits).
  - **Cost:** Low.
  - **Best For:** General-purpose RAG pipelines using standard text documents, articles, or PDFs.

- **Semantic Chunking**

  - **Granularity:** Topic-based transitions detected via embedding distance thresholds.
  - **Coherence:** High (groups text by shared meaning and topic drift).
  - **Cost:** Medium (requires running text through embedding models during preprocessing).
  - **Best For:** In-depth research papers, long-form articles, and multi-topic content.

- **Document-Based Chunking**

  - **Granularity:** Structural elements (Markdown headers, HTML sections, XML tags).
  - **Coherence:** High (respects author-defined document hierarchy).
  - **Cost:** Low to Medium.
  - **Best For:** Structured technical documentation, user manuals, and API guides.

- **LLM/Agentic Chunking**
  - **Granularity:** Fully contextual and dynamic.
  - **Coherence:** Exceptional (an LLM evaluates context and boundaries to synthesize optimal chunks).
  - **Cost:** High (requires frequent LLM inference calls).
  - **Best For:** Complex legal documents, financial reports, or highly interconnected context where subtle nuance is critical.

# Similarity Search Types

> **Overview:** How a vector database measures "closeness"—combining metrics that score vector proximity with index structures that enable fast retrieval at scale.

---

## Distance & Similarity Metrics

Metrics score the geometric relationship and distance between vector representations.

| Metric                | Core Concept                            | Characteristics & Use Cases                                                                     |
| --------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **Cosine Similarity** | Angle between vectors                   | Ignores vector magnitude. The default standard for text embeddings.                             |
| **Dot Product**       | $\text{Cosine} \times \text{Magnitude}$ | Rewards larger vectors. Ideal when vector magnitude carries semantic meaning.                   |
| **Euclidean (L2)**    | Straight-line distance                  | Measures direct distance between points in space; smaller distance indicates higher similarity. |
| **Manhattan (L1)**    | Sum of absolute differences             | Grid-based distance metric; robust and stable in high-dimensional spaces.                       |

---

## Approximate Nearest-Neighbor (ANN) Indexes

Indexes structure vector storage to enable sub-linear search times across large-scale datasets.

| Index Type             | Traversal Strategy     | Performance & Trade-offs                                                                                        |
| ---------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Flat / Brute-Force** | Exhaustive search      | Compares query vector to every stored vector. Yields exact results, but slow; suitable only for small datasets. |
| **HNSW**               | Graph-based traversal  | Navigates hierarchical graph nodes. Fast and accurate; the most popular production index at scale.              |
| **IVF**                | Partition clustering   | Clusters vectors during ingestion and searches only within the nearest cluster centroids.                       |
| **LSH / PQ**           | Hashing & Quantization | Compresses vectors into compact hash signatures or codebooks for memory-efficient search.                       |

## Re-Ranking in Retrieval-Augmented Generation (RAG)

## Overview

Retrieval-Augmented Generation (RAG) systems rely on pairwise sentence scoring at varying levels of granularity (based on data chunking strategy) to retrieve relevant context before passing it to an LLM for generation. Re-ranking acts as a precision layer following initial vector retrieval.

---

## Limitations of First-Stage Retrieval

First-stage retrieval (e.g., standard vector search using bi-encoders) introduces several systemic trade-offs:

- **Approximate Neighbors $\neq$ Relevant Docs:** Approximate Nearest Neighbor (ANN) search optimizes for retrieval speed rather than deep semantic precision.
- **Semantic Drift in Embeddings:** High vector similarity does not automatically guarantee a contextually appropriate answer.
- **Query-Document Length Mismatch:** Embedding performance degrades when pairing short search queries with long document chunks.
- **Lack of Cross-Attention:** Bi-encoders embed queries and documents independently, missing vital token-to-token interactions.

---

## How Re-Ranking Resolves Retrieval Bottlenecks

Re-ranking introduces a two-stage retrieval pipeline that bridges the gap between speed and precision:

| First-Stage Issue                | Re-Ranking Solution                | Core Benefit                                                                  |
| -------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------- |
| Speed prioritized over precision | **Cross-Encoder Scoring**          | Computes full attention across query and document tokens together.            |
| Broad, noisy top-$K$ matches     | **Targeted Candidate Re-ordering** | Focuses on a smaller candidate set to maximize accuracy at a localized scale. |
| Absence of reasoning             | **LLM-Based Re-rankers**           | Utilizes models like Cohere Rerank or GPT-4 to judge relevance contextually.  |
| Suboptimal metric performance    | **Benchmarked Quality Boost**      | Delivers typical gains of +20–40% in precision on MRR and NDCG metrics.       |

---

## Summary Takeaways

1. **Bi-Encoders (Stage 1):** Scale speed by retrieving broad context across large vector databases.
2. **Cross-Encoders (Stage 2):** Maximize precision by re-scoring top candidates with query-document cross-attention.
3. **End Result:** Provides cleaner, highly relevant context to the LLM, reducing hallucinations and improving output quality.

## Re-Ranking

### 1. Cross-Encoder

- **Tag:** Most Accurate
- **Description:** Concatenates `[CLS]` query `[SEP]` document and scores jointly via BERT/RoBERTa. Full attention across both → captures fine-grained interactions.
- **Pros (✓):** Highest quality. State-of-the-art on BEIR.
- **Cons (X):** O(K) inference passes — expensive for large K.
- **Examples:** _ms-marco-MiniLM, monoT5, BGE-Reranker_

### 2. ColBERT / Late Interaction

- **Tag:** Efficient
- **Description:** Embeds query and doc token-by-token; scores via MaxSim over token-level dot-products. Bridges bi-encoder speed and cross-encoder quality.
- **Pros (✓):** Sub-millisecond re-ranking at query time.
- **Cons (X):** Large index footprint (one vector per token).
- **Examples:** _ColBERT v2, PLAID index_

### 3. LLM-Based Re-Ranking

- **Tag:** Reasoning
- **Description:** Prompts a generative LLM (GPT-4, Claude, Cohere) to judge relevance or produce a ranking. Uses listwise or pointwise prompting strategies.
- **Pros (✓):** Flexible — handles edge cases, multilingual.
- **Cons (X):** High latency & cost; not deterministic.
- **Examples:** _Cohere Rerank 3, RankGPT, LLM-RankFusion_

### 4. Scores & Heuristics

- **Tag:** Fast Baseline
- **Description:** BM25 re-scoring, query coverage ratios, passage position bias, or simple linear re-weighting of the first-stage scores with additional signals.
- **Pros (✓):** Zero extra model cost; very low latency.
- **Cons (X):** Limited precision gains; brittle on semantics.
- **Examples:** _Query-term coverage, BM25 re-score, score interpolation_

## Hallucination Resistance

## How RAG cuts hallucination

- **Evidence-conditioned answers**
  - The model writes from retrieved passages, not from fuzzy memory.
- **Built-in citations**
  - Each claim can point back to a source chunk for verification.
- **"Answer only from context" prompting**
  - Instruct the LLM to refuse when the context lacks the answer.
- **Fresh, swappable knowledge**
  - Update the index to correct facts instantly — no retraining.

---

## ...and where it still fails

- **Retrieval is the ceiling**
  - Miss the right chunk and the answer is wrong — "garbage in, garbage out."
- **Context can be ignored**
  - The model may override evidence with its own parametric beliefs.
- **Conflicting / stale sources**
  - Contradictory chunks produce confident but muddled answers.

### Mitigation Strategies

> **Mitigate:** groundedness scoring (RAGAS), context-relevance filters, and an explicit "I don't know" fallback.
