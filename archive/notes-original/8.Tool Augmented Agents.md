# A Frozen Model Can Predict — But It Can't Act

> _Out of the box, an LLM is a text-in / text-out function with a fixed knowledge cutoff. Tools close the gap between knowing and doing._

---

## Model Alone vs. Model + Tools

- **Model Alone:**

  - **Stale knowledge:** Nothing past the training cutoff; no live prices, news, or your private data.
  - **Unreliable computation:** Arithmetic and precise logic drift — the model approximates, it doesn't calculate.
  - **No side effects:** Can't query an API, write a file, or trigger an action in the real world.

- **Model + Tools:**
  - **Reach beyond the prompt:** Search the web, hit internal APIs, read a database — fetch fresh, grounded facts on demand.
  - **Offload exact work:** Hand math, code, and structured logic to deterministic tools that get it right every time.
  - **Take real actions:** Generate an image, send a request, update a record — the model decides, the tool executes.

# The Tool-Calling Loop

> _The model never runs code itself. It requests a call; your runtime executes it and returns the result; the model continues — repeating until it can answer._

---

## Step-by-Step Flow

1. **User Query:** A request that needs facts, math, or an action.
2. **Model Reasons:** Decides whether to answer directly or call a tool.
3. **Tool Call Emitted:** Structured JSON: tool name + arguments.
4. **Runtime Executes:** Your code runs the function / API call.
5. **Result Returned:** Output is fed back into the conversation.
6. **Answer Composed:** Model synthesizes a grounded final reply.

---

> **Note:** Steps 2–5 repeat for multi-tool tasks — the model can call several tools in sequence before answering.

# Function Calling: Structured Requests, Your Execution

---

## Mechanics & Workflow

- **Register tools as schemas:** Each tool has a name, a plain-language description, and a JSON Schema for its parameters.
- **The model requests, never runs:** Given available tools, it emits a `tool_calls` object with the chosen tool name and typed arguments.
- **You execute & feed back:** Your runtime executes the requested function, then appends the result as a tool message back to the model.
- **The model decides when:** Driven by tool descriptions, the model decides whether to answer directly, call one tool, or chain several.

---

## Schema & Response Example

```python
# tool schema -> model response

tools = [{
    "name": "get_weather",
    "description": "Live weather for a city",
    "parameters": {
        "city": { "type": "string" }
    }
}]

# model returns, it does not run:
tool_calls: [{ "name": "get_weather",
               "arguments": { "city": "Karachi" } }]
```

# A Working Taxonomy of Tools

> _Anything you can wrap in a function with a clear description can become a tool. These six families cover most agent designs._

---

## Tool Families

- **Compute & Code:** Calculator, Python sandbox, unit conversion — exact, deterministic results.
- **Search & Retrieval:** Web search, vector / RAG lookup, documentation — fresh, grounded context.
- **Data & APIs:** SQL queries, internal services, third-party APIs — live and private data.
- **Generation:** DALL·E images, charts, document drafting — produce new artifacts.
- **Actions & Effects:** Send email, create a ticket, update a record — change the outside world.
- **Custom Functions:** Any business logic you expose — pricing, scoring, workflow steps.

# API Chaining: The Output of One Feeds the Next

> _Many tasks can't be solved by a single call. The agent passes state forward — each tool consumes the previous result and produces the next input._

---

## Sequential Tool Pipeline

1. **Geocode:** `"Karachi"` $\rightarrow$ `lat, lng`
2. **Weather API:** `lat, lng` $\rightarrow$ `forecast`
3. **Compute:** `forecast` $\rightarrow$ `packing score`
4. **Summarize:** $\rightarrow$ `natural-language answer`

---

## Execution Modes

- **Sequential:** Each step depends on the last. State threads through; order matters; latency adds up.
- **Parallel:** Independent calls fire at once, then merge — faster, but only when steps don't depend on each other.

# DALL·E: Image Generation as a Tool

> _Generation tools fit the same pattern as any other. The model emits a prompt; the image API returns a URL or base64 payload that the agent can display, save, or pass downstream._

---

## Core Mechanics

- **Text prompt in:** A descriptive natural-language prompt — subject, style, composition, lighting.
- **Image out:** Call `images.generate` with model, size, and count; receive a URL or b64 string.
- **Wrap as a callable:** Expose it as a tool so the agent can invoke generation mid-task, on its own.

---

## Example Prompt

> _"A minimalist isometric icon of a robot connecting to gears and a database, navy & blue, white background"_

---

## Where It Earns Its Keep

- Marketing & concept visuals from a brief
- Mockups, placeholders & UI exploration
- Illustrating reports & decks on demand
- Mind cost, latency & content-safety limits

# LangChain: Tools, Agents & the Reason–Act Loop

---

## Core Mechanics

- **`@tool` wraps a function:** Decorate any Python function with a name + docstring and it becomes an agent-callable tool.
- **AgentExecutor runs the loop:** `bind_tools` / `create_tool_calling_agent` give the model the tool set and drive iteration.
- **ReAct pattern:** `think` $\rightarrow$ `act` $\rightarrow$ `observe` — the agent reasons, calls a tool, reads the result, and repeats until the goal is met.

---

## Tool Definition Example

```python
@tool
def search_docs(query: str) -> str:
    """Search internal docs for a query."""
    return retriever.invoke(query)
```

---

## The ReAct Execution Cycle

1. **Thought:** Reason about the next step.
2. **Action:** Call the chosen tool.
3. **Observation:** Read the tool's result.

_↺ Loops continuously until the answer is ready._

# Tool Routing

> _With many tools available, the agent must choose. Selection is driven mostly by the tool descriptions which makes good descriptions a routing problem, not a cosmetic one._

---

## Routing Example Flow

- **User Query:** _"What's 18% of last month's revenue?"_
- **Selected Tools:**
  - `query_revenue` — Fetch the figure
  - `calculator` — Compute 18%
- **Unselected Tool:**
  - `web_search` — Not selected

---

## Routing Mechanisms

- **LLM Router:** Model reads descriptions and decides dynamically.
- **Semantic Router:** Embed the query and match to the nearest tool vector.
- **Rule-Based:** Apply deterministic keyword or pattern logic.

# Agent Composition

> _As tasks grow, one agent with many tools gives way to multiple specialized agents coordinated by an orchestrator — each focused, each easier to reason about._

---

## Supervisor Pattern Architecture

`[Orchestrator]` $\rightarrow$ Delegates tasks to specialist agents and merges their work:

- **Research Agent:** Data gathering and retrieval
- **Analysis Agent:** Computation and reasoning
- **Creative Agent:** Content generation and output

---

## Composition Patterns

- **Sequential:** A pipeline; each agent's output feeds the next.
- **Hierarchical:** A supervisor delegates to and reviews workers.
- **Network:** Peers hand off to each other as needed.

---

## When to Split into Multiple Agents

- Distinct specializations or tool sets per role
- Context windows get crowded with one agent
- Separation of concerns aids testing & safety
- Steps can run in parallel for speed

# Lab 3 — Multi-step Task Agent with Chained Tools

---

## Overview

- **Scenario:** Give one agent search, calculator, and DALL·E. Ask it to research a topic, compute a figure, and produce a matching visual — in one run.
- **Outcome:** A capstone agent that plans, routes, chains, and composes — the full pattern, end to end.

---

## Build Steps

1. **Register the full tool set:** Search, calculator, and image-generation, each with a precise, routing-ready description.
2. **Let the agent plan & route:** It selects tools per sub-goal — no hard-coded order; routing is the model's job.
3. **Chain outputs across steps:** Search feeds the calculation; the result shapes the image prompt.
4. **Synthesize the deliverable:** The agent returns a written answer plus the generated asset, with guardrails on iterations.

# Best Practices & Pitfalls

> _Building agents that hold up in production requires clear routing descriptions, strict input validation, resilient error handling, and defensive execution guardrails._

---

## Core Guidelines

- **Write precise descriptions:** Routing lives or dies on tool descriptions. Be specific about what each tool does and when to use it.
- **Validate every argument:** Treat model-generated args as untrusted input — type-check, bound, and sanitize before executing.
- **Handle tool errors:** Return failures back to the model as observations so it can retry or pick another path.
- **Cap the loop:** Set a max-iteration limit so a confused agent can't chain tool calls forever.
- **Watch cost & latency:** Every tool call is a round trip. Batch, cache, and prune the tool set to what's needed.
- **Least privilege & secrets:** Scope tool permissions tightly; never expose raw env or secrets to the model.
